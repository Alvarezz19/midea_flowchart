# 美的暖通/楼宇控制 JSON 流程图生成系统设计方案

## 1. 方案定位

本方案用于指导后续开发“美的暖通/楼宇控制 JSON 程序流程图生成工具”。系统目标是：用户输入或上传美的编程平台导出的 JSON 项目代码后，自动生成用户友好的流程图，并支持逐层下钻、点位追踪、命名规则校验和 AI 辅助解释。

当前项目中已有以下基础材料：

- `programs/`：AHU 程序、机房群控程序、风冷热泵标准程序样例。
- `文档/1.命名规则v20191011B.XLSX`：命名规则原始文件。
- `data/naming_rules.json`、`data/naming_rules.sqlite`：命名规则结构化结果。
- `configs/domain_profiles/ahu.json`、`configs/domain_profiles/chiller_plant.json`、`configs/domain_profiles/air_source_heat_pump.json`：领域 profile 雏形。
- `示例.png`：期望的“抽象流程图”方向参考。
- `文档/AHU程序结构对比总结.md`、`文档/机房群控程序JSON结构对比总结.md`：样例 JSON 结构分析结论。

本方案的核心判断是：系统不应复刻美的编程平台的原始节点画布，而应构建“工程逻辑说明图 + 原始节点可追溯”的多层视图。

## 2. 设计信心与边界

本方案基于当前仓库中 5 个样例 JSON 的共同结构特征制定：

- 顶层是扁平数组。
- `type = tab` 表示页签。
- `type = subflow` 表示子流程定义。
- `type = subflow:<id>` 表示子流程实例。
- 普通节点通过 `z` 归属于某个页签或子流程。
- 节点包含 `inputs`、`outputs`、`x`、`y`、`wires`。
- 当前样例中的 `wires` 更接近“当前节点输入端引用上游节点”，而不是标准 Node-RED 风格的“当前节点输出端连接下游节点”。

因此，第一版可以有较高信心处理当前美的编程平台导出的同类 JSON。但必须承认以下边界：

- 新 JSON 可能出现未知节点类型、未知页签、未知子流程、未知点位命名。
- 不同项目的业务抽象粒度可能不同，不能只按三山经开区 AHU 程序写死规则。
- 命名规则库与项目点位并非一一完全匹配，必须允许“未匹配”和“冲突候选”状态。
- AI 只能作为解释、归类和命名候选工具，不能替代确定性解析和命名校验。

本方案的设计原则是：解析层通用，抽象层可配置，展示层可降级，未知内容可见。

## 3. 用户与使用场景

### 3.1 主要用户

1. 甲方或管理人员

关注系统由哪些部分组成、控制流程是否合理、文档是否清晰，不关心几百个原始节点如何接线。

2. 暖通/楼控工程人员

关注输入点、输出点、控制模块、联锁条件、点位命名、项目差异。

3. 程序开发和调试人员

关注原始节点、连线、子流程实例、输入输出端口、变量追踪。

4. 交付和文档人员

关注能否导出图纸、说明、命名异常清单、项目概览。

### 3.2 核心场景

- 上传或粘贴 JSON，自动生成项目总览图。
- 点击 `IO/通讯`、`控制`、`定时`、`直膨机状态` 等区块查看详情。
- 搜索 `SF_RUN`、`SA_T`、`ZP_F`、`直膨总故障` 等点位并定位到图中。
- 查看某个输出命令受哪些输入、条件和中间变量影响。
- 查看点位是否符合 `1.命名规则v20191011B.XLSX` 的命名规则。
- 对未匹配点位查看候选标准命名。
- 导出甲方可读的流程图和说明。

## 4. 产品形态

### 4.1 总体形态

产品应采用“数据密集型工程看板 + 可交互流程图”的形态。

推荐布局：

```text
--------------------------------------------------------------+
| 顶部工具栏：上传 JSON / 示例项目 / 搜索 / 视图切换 / 导出        |
+------------+-----------------------------------+-------------+
| 左侧导航    | 中间流程图画布                      | 右侧详情面板 |
|            |                                   |             |
| 项目结构树  | 总览图 / 模块图 / 原始节点图         | 模块说明     |
| 页签列表    | 支持缩放、拖拽、点击、框选           | 输入输出     |
| 模块列表    |                                   | 命名校验     |
| 异常清单    |                                   | 原始节点     |
+------------+-----------------------------------+-------------+
| 底部状态栏：解析状态 / 节点数量 / 命名匹配率 / 未识别数量          |
+--------------------------------------------------------------+
```

### 4.2 三层视图

系统必须提供三层视图，而不是单一大图。

#### 4.2.1 第一层：系统总览图

目标用户：甲方、管理人员、工程负责人。

目标：第一眼看懂系统结构。

AHU 程序的总览图建议如下：

```text
现场输入 / 通讯输入
        |
        v
IO/通讯 ---------------------> 内部变量 / BACnet 点
        |                              |
        v                              v
直膨机状态 -------------------> 控制逻辑 <------ 定时使能
                                       |
                                       v
                           执行输出 / 通讯输出 / 状态反馈
```

总览图节点不应超过 8 到 12 个。每个区块显示摘要：

- 页签名称。
- 节点数量。
- 点位数量。
- 子流程实例数量。
- 命名未匹配数量。
- 未识别模块数量。

#### 4.2.2 第二层：模块详情图

目标用户：暖通/楼控工程人员。

目标：理解某个页签内部有哪些功能模块，以及模块之间的数据流。

例如 `控制` 页应抽象为：

```text
系统运行条件
        |
        v
模式判断 / 季节判断
        |
        +------------------+
        |                  |
        v                  v
送风机控制           温湿度控制
        |                  |
        v                  v
频率控制             冷水阀 / 电加热 / 风阀控制
        |                  |
        +--------+---------+
                 v
           输出命令 / 状态反馈
```

例如 `IO/通讯` 页应抽象为：

```text
物理输入       通讯输入       调用信号
   |             |             |
   +-------------+-------------+
                 v
       点位标准化 / 内部变量
                 |
       +---------+----------+
       |                    |
       v                    v
  控制模块使用          物理/通讯输出
```

例如 `直膨机状态` 页不应强行画成复杂流程图，而应采用“映射流 + 状态矩阵”：

```text
Modbus 状态寄存器
        |
        v
直膨状态解析与倍率换算
        |
        v
标准状态点 / BACnet 点
```

并在详情面板或下方表格中展示：

- 外机基础状态。
- 压缩机频率和电流。
- 冷凝/蒸发温度。
- 冷凝/蒸发压力。
- 膨胀阀开度。
- 软件版本、外机地址、匹数。

#### 4.2.3 第三层：原始节点图

目标用户：开发和调试人员。

目标：保留原始 JSON 的可追溯能力。

此视图可接近美的编程平台画布，但必须增强以下能力：

- 自动定位某个节点。
- 高亮上下游。
- 只显示选中模块相关节点。
- 支持原始坐标和自动布局切换。
- 支持按节点类型过滤。
- 支持从抽象模块跳转到原始节点集合。

原始节点图不应作为默认视图，因为它对甲方和非开发人员不友好。

## 5. 流程图视觉设计

### 5.1 视觉原则

- 工程化、清晰、克制。
- 信息密度高，但默认不拥挤。
- 避免装饰性大屏风格。
- 避免一张图塞下所有节点。
- 所有颜色都必须有语义。
- 命名异常、未知模块、冲突候选必须明显可见。

### 5.2 颜色语义

建议第一版使用以下语义色：

| 类型 | 颜色建议 | 用途 |
| --- | --- | --- |
| 物理输入 / 采集 | 蓝色 | `hwInput`、传感器、DI、AI |
| 通讯输入 / 通讯输出 | 紫色 | `modbusOutput`、通讯寄存器、直膨状态 |
| 内部变量 / BACnet | 灰蓝色 | `swInput`、内部点、BACnet 可见点 |
| 控制逻辑 | 绿色 | `logic`、`switch`、`compare`、`limit` |
| PID / 算法 | 橙色 | `pid`、焓值、含湿量、温湿度算法 |
| 执行输出 | 深绿色 | `hwOutput`、最终命令、阀门/风机命令 |
| 故障 / 报警 | 红色 | 故障、报警、保护、滤网 |
| 未匹配命名 | 黄色或红色描边 | 未找到命名规则 |
| 未识别模块 | 灰色虚线框 | 可解析但未能业务归类 |

### 5.3 连线语义

| 连线 | 含义 |
| --- | --- |
| 实线箭头 | 确定的数据/控制关系 |
| 虚线箭头 | 引用关系、间接关系、跨页引用 |
| 加粗箭头 | 主控制链路 |
| 灰色细线 | 辅助信号 |
| 红色线 | 故障、保护、报警链路 |

### 5.4 模块卡片信息

总览和模块图中的节点卡片建议包含：

```text
模块名称
角色标签 / 页签
节点数  点位数  输出数
命名：已匹配 x / 未匹配 y / 冲突 z
```

不建议在卡片内显示大量原始节点名。长列表应放到右侧详情面板。

## 6. 数据解析设计

### 6.1 解析目标

解析层的目标是把任意项目 JSON 转换为统一中间模型。解析层不得依赖三山经开区的具体页签名、点位名或坐标。

### 6.2 输入校验

用户上传 JSON 属于系统边界，必须做输入校验：

- JSON 格式是否合法。
- 顶层是否为数组。
- 每个对象是否至少有 `id` 和 `type`。
- `id` 是否重复。
- `wires` 是否为数组或可视为缺省空连接。
- `z` 指向的页签或子流程是否存在；不存在时标记为悬空归属。

内部解析过程中不要为不可能发生的内部状态添加过度防御；但对用户输入和外部文件必须做明确校验和错误提示。

### 6.3 中间模型

建议定义如下核心模型：

```text
ProjectModel
  source
  rawObjects
  tabs
  subflows
  nodes
  edges
  points
  moduleInstances
  diagnostics

TabModel
  id
  label
  role
  nodeIds
  stats

SubflowModel
  id
  name
  inputs
  outputs
  internalNodeIds

NodeModel
  id
  type
  z
  name
  inputs
  outputs
  x
  y
  raw
  role
  point
  namingStatus

EdgeModel
  id
  sourceNodeId
  sourcePort
  targetNodeId
  targetPort
  relationType
  confidence

PointModel
  nodeId
  rawName
  displayName
  standardName
  bacnetObjectPrefix
  pointKind
  group
  namingStatus

ModuleModel
  id
  label
  role
  tabId
  nodeIds
  inputPointIds
  outputPointIds
  childModuleIds
  summary
```

### 6.4 连线解析规则

当前样例 JSON 中，`wires` 在多数场景下表示“当前节点输入端口引用哪些上游节点”。因此解析边时应采用：

```text
for each targetNode:
  for each targetPortIndex in targetNode.wires:
    for each upstreamRef in targetNode.wires[targetPortIndex]:
      source = upstreamRef.id
      sourcePort = upstreamRef.port
      target = targetNode.id
      targetPort = targetPortIndex
```

生成：

```text
sourceNodeId -> targetNodeId
```

也就是说，图模型中的边方向应表达“数据或控制信号从上游节点流向当前节点”。

### 6.5 页签识别

页签识别不能写死完整名称，应通过 domain profile 识别。

例如 AHU profile：

```text
包含 IO 和 通讯 -> io_comm
包含 控制 -> control
包含 定时 -> schedule
包含 直膨机状态 -> dx_status
包含 直膨机故障 -> dx_fault
包含 排风机 -> exhaust_fan
```

如果无法匹配，则标记：

```text
role = unknown_tab
label = 原始页签名
```

未知页签必须进入总览图，不能丢弃。

### 6.6 程序类型识别

程序类型识别顺序建议：

1. 根据文件路径和目录名识别，如 `AHU程序`、`机房群控程序`。
2. 根据页签名称匹配 profile。
3. 根据子流程名称、点位前缀、关键节点类型辅助判断。
4. 如果多个 profile 匹配，给出候选并选择置信度最高者。
5. 如果仍无法判断，使用通用 profile。

通用 profile 至少支持：

- 页签列表。
- 节点类型统计。
- 连接解析。
- 点位清单。
- 原始节点图。
- 未归类模块。

## 7. 抽象流程图生成设计

### 7.1 抽象原则

流程图不是原始节点图的缩小版，而是业务逻辑的重新表达。

抽象应遵循：

- 先按页签形成一级结构。
- 再按子流程实例、点位分组、连接密度、注释和空间布局形成模块。
- 优先展示主流程，辅助信号可收起。
- 重复结构用集合或矩阵表达，不逐个平铺。
- 不确定归类必须标记，不允许伪装成确定结果。

### 7.2 模块识别规则

模块识别建议采用确定性规则优先：

1. 子流程实例直接成为模块。

例如：

- `末端组空送风机标准控制`
- `7档电加热`
- `末端组空冷水阀开度控制`

2. 根据页签角色生成默认模块。

例如 AHU：

- `io_comm`：物理输入、通讯输入、内部变量、物理/通讯输出。
- `control`：系统运行、模式判断、风机控制、温湿度控制、阀门控制、故障联锁。
- `schedule`：定时使能。
- `dx_status`：直膨状态映射。

3. 根据点位前缀和关键词聚合。

例如：

- `SF`、`送风机` -> 送风机。
- `EF`、`排风机` -> 排风机。
- `ZP`、`直膨`、`外机`、`EXV` -> 直膨机。
- `CWV`、`冷水阀` -> 冷水阀。
- `EH`、`电加热` -> 电加热。
- `CO2` -> CO2 控制。

4. 根据注释节点辅助识别区域。

注释节点不能作为唯一依据，但可用于模块标题和分区提示。

5. 根据画布坐标辅助识别局部组。

如果同一页签中存在空间上明显聚集的一批节点，可作为候选模块，但坐标只作为辅助，不能作为唯一业务规则。

6. 根据连接社区辅助识别。

对高密度连接子图可生成候选模块，但需要通过点位名称或节点类型再命名。

### 7.3 抽象层级

建议定义 4 个层级：

| 层级 | 名称 | 用途 |
| --- | --- | --- |
| L0 | 项目概览 | 文件信息、页签、统计、命名匹配率 |
| L1 | 系统总览图 | 甲方可读的大区块流程 |
| L2 | 页签/模块详情图 | 工程人员理解模块关系 |
| L3 | 原始节点追踪图 | 开发和调试追踪原始连接 |

系统默认进入 L1。

### 7.4 AHU 总览图规则

AHU 程序总览图默认包含：

- `IO/通讯`
- `定时`
- `控制`
- `直膨机状态`
- 如果存在：`排风机`
- 如果存在：`直膨机故障`
- 如果存在未知页签：`未识别页签`

推荐主链路：

```text
IO/通讯 -> 控制 -> 输出命令
定时 -> 控制
直膨机状态 -> 控制
控制 -> IO/通讯
IO/通讯 -> 直膨机状态
```

这里的连线并非简单统计所有原始边，而是抽象表达功能关系。系统应在详情中说明每条抽象边由哪些原始点位或节点支持。

### 7.5 控制页详情规则

AHU 控制页建议优先识别以下模块：

- 系统运行/故障/模式判断。
- 定时允许和系统使能。
- 送风机启停联锁。
- 送风机频率控制。
- 排风机/回风机控制。
- 温度设定与限幅。
- 湿度设定与除湿/加湿。
- 冷水阀/热水阀/冷热水阀控制。
- 电加热/电预热控制。
- 新风阀/回风阀/排风阀控制。
- 直膨机开关机、模式、设定温度。
- BACnet/内部状态反馈。

如果某模块无法识别完整输入输出，也应显示“识别不完整”，并列出原因：

- 无明确输出点。
- 无标准命名匹配。
- 子流程接口无法解析。
- 仅发现零散节点。

### 7.6 IO/通讯页详情规则

IO/通讯页建议按信号边界，而不是原始坐标组织：

- 物理输入：`hwInput`、AI、DI。
- 物理输出：`hwOutput`、AO、DO。
- 通讯输入/输出：`modbusOutput` 及其读写属性。
- 内部软件点：`swInput`。
- BACnet 可见点：`bacnetVisible = true`。
- 调用信号和跨页引用：`quote`。

详情图中应突出：

```text
现场/设备 -> 原始采集点 -> 内部变量 -> 控制模块 -> 输出点
```

### 7.7 直膨机状态页详情规则

直膨机状态页属于重复映射结构，应采用“分组 + 表格 + 少量流程图”。

建议分组：

- 外机基础信息：软件版本、地址、匹数。
- 系统信息：外机台数、系统匹数、外机模式。
- 压缩机：频率、交流电流、直流母线电流。
- 温度：冷凝温度、蒸发温度。
- 压力：冷凝压力、蒸发压力。
- EXV：膨胀阀开度。

当出现 1、2、3、4 号外机等重复结构时，用矩阵展示：

```text
指标 \ 外机      1号      2号      3号      4号
软件版本         E1       F1       G1       ...
外机地址         E2       F2       G2       ...
压缩机频率1      E4       F4       G4       ...
冷凝温度         E10      F10      G10      ...
```

### 7.8 定时页详情规则

定时页通常较小，可直接保留完整逻辑图。

三山经开区 AHU 中可表达为：

```text
TIME_EN
   |
   +----> 与 ----> TIME_CST
   |
SP0
```

并附说明：

```text
TIME_CST 表示定时允许输出，由 TIME_EN 和 SP0 共同决定。
```

## 8. 命名规则设计

### 8.1 命名规则目标

系统必须基于 `data/naming_rules.json` 校验流程图中的点位命名。

目标不是强行让所有点位都匹配，而是给出清晰状态：

- 已匹配。
- 多候选冲突。
- 未匹配。
- 无需匹配。

### 8.2 命名匹配输入字段

应从以下字段提取候选名称：

- `name`
- `bacnetObjectPrefix`
- `label`
- `labelName`
- `modbusSlaveRegAddr` 结合通讯上下文
- `hwInputMode` / `hwOutputMode` 结合硬件上下文
- `quote` 的引用标签
- 子流程端口名称

不同节点类型优先级不同：

| 节点类型 | 优先字段 |
| --- | --- |
| `swInput` | `bacnetObjectPrefix`、`name` |
| `hwInput` | `name`、硬件通道信息 |
| `hwOutput` | `name`、硬件通道信息 |
| `modbusOutput` | `name`、通讯寄存器信息 |
| `quote` | 引用源点名称 |
| `subflow:*` | 子流程端口名、连接点位名 |

### 8.3 命名匹配策略

建议分 5 级：

1. 精确匹配

完全匹配 `object_name_norm` 或别名。

2. 规整匹配

统一大小写，去除空格、下划线、斜杠、括号、中文标点后匹配。

3. 前缀匹配

用于带编号或设备序号的点位，例如 `SF_RUN`、`SF1_RUN`、`ZP_A1`。

4. 中文语义别名匹配

通过中文描述、状态对、单位状态等别名匹配。

5. AI 候选建议

只在确定性匹配失败时生成候选，不直接判定为已匹配。

### 8.4 命名状态

建议定义：

```text
matched
  已唯一匹配命名规则。

conflict
  命中多个候选，需要人工确认。

unmatched
  未命中规则。

ignored
  通用占位名称，例如“变量”，不计入命名问题，但应在详情中显示。

not_applicable
  算子节点、逻辑节点等非点位节点。
```

### 8.5 图上的呈现

图中默认显示：

```text
中文业务名
标准对象名
原始名称
```

例如：

```text
送风机运行状态
SF_RUN
原始：[AV-18][MS#37]SF_RUN
```

未匹配时：

```text
直膨总故障
ZP_F
命名规则：未匹配
```

冲突时：

```text
主机运行
候选：CH_RUN / HP_RUN
状态：需确认
```

### 8.6 命名异常清单

左侧导航或底部面板应提供命名异常清单：

- 未匹配点位。
- 多候选点位。
- 使用通用名称的点位。
- 同一标准名对应多个原始点位。
- 同一原始名对应多个节点。

清单项点击后定位到图中节点。

## 9. AI 功能设计

### 9.1 AI 的正确定位

AI 不应负责底层解析，也不应凭空决定连接关系。AI 的职责是：

- 解释模块。
- 辅助点位归类。
- 给未匹配点位提供候选命名。
- 根据用户角色生成不同粒度说明。
- 帮助用户理解某个输出受哪些条件影响。

确定性解析和命名规则校验必须由程序完成。

### 9.2 第一版 AI 功能

建议第一版只做 4 个 AI 功能：

1. 模块说明生成

输入：模块名称、页签角色、输入点、输出点、关键节点类型、子流程名称。

输出：

```text
该模块负责根据系统运行状态、定时允许、送风机故障反馈和手自动状态生成送风机启停命令。
```

2. 未匹配命名候选

输入：原始点名、上下游点位、所属模块、命名规则候选集。

输出：

```text
候选标准名：
1. ZP_F：直膨总故障，置信度高
2. DX_F：直膨故障，置信度中
```

AI 输出必须标记为“建议”，不能直接写入规则库。

3. 复杂链路解释

输入：某个输出点的上游追踪子图。

输出：按条件分组解释。

4. 汇报版说明

输入：总览图结构、模块摘要、命名异常统计。

输出：甲方可读的项目流程说明。

### 9.3 AI 安全边界

- AI 不能新增 JSON 中不存在的节点或连线。
- AI 不能把未匹配点位自动标记为已匹配。
- AI 不能覆盖用户确认过的命名结果。
- AI 回答必须引用来源节点 ID、点位名或模块 ID。
- 如果启用外部模型，应在产品上明确提示用户项目 JSON 可能被发送到模型服务；企业交付场景建议支持本地关闭 AI。

## 10. 技术架构建议

### 10.1 总体架构

建议采用前后端分层：

```text
前端
  上传/选择 JSON
  流程图画布
  详情面板
  搜索和筛选
  导出

后端或本地解析服务
  JSON 解析
  中间模型生成
  命名规则匹配
  模块抽象
  AI 上下文构造

数据层
  domain profiles
  naming rules
  sample programs
  用户确认映射
```

### 10.2 前端图形库

建议使用 React + TypeScript + `@xyflow/react` 作为交互流程图基础。

理由：

- 官方文档明确其核心模型是 nodes、edges 和 viewport，符合本项目的图模型。
- 支持自定义节点，适合做工程模块卡片。
- 支持控制器、背景、视口等交互组件。
- 当前包名为 `@xyflow/react`，不是旧的 `reactflow` 包名。

布局算法建议：

- 第一版总览图和模块图优先使用手写规则布局或 Dagre。
- 对复杂模块和跨层级布局，可评估 ELK。
- 原始节点图默认使用 JSON 中的 `x`、`y` 坐标，并提供自动布局切换。

注意：

- Dagre 更适合有向层级图，配置简单。
- ELK 配置能力更强，支持更复杂的布局和边路由，但复杂度更高。
- 不建议第一版就追求完美自动布线，应先保证抽象结构正确。

### 10.3 后端或解析核心

建议解析核心用 Python 或 TypeScript 都可以，但应独立于 UI：

```text
parseJsonToProjectModel()
buildEdges()
matchNamingRules()
detectDomainProfile()
buildOverviewGraph()
buildTabDetailGraph()
buildRawNodeGraph()
```

考虑到当前项目已有 Conda 环境、命名规则来自 Excel/SQLite，Python 更适合作为第一版解析与规则引擎。前端可通过 API 调用，也可以先通过 CLI 生成中间 JSON 给前端加载。

```text

  api/

  web/
    ...
tests/
  fixtures/

```

如果采用纯前端 MVP，也应保留类似模块边界，不要把解析逻辑写进 React 组件。

## 11. 兼容性策略

### 11.1 防止被三山经开区绑定

三山经开区 AHU 程序只能作为第一条验收样例，不能作为唯一规则来源。

禁止硬编码：

```text
页签完整名：IO/通讯(三山经开）
项目名称：三山经开区
具体节点 ID
具体坐标
具体点位完整名
```

允许配置化：

```text
页签包含 IO 和 通讯 -> io_comm
点位前缀 SF -> 送风机
节点类型 pid -> 算法控制
子流程名称包含 风机 -> 风机控制
```

### 11.2 多样例回归

第一版开发时必须同时跑以下样例：

- `programs/AHU程序/三山经开区/flows_20251210190941.json`
- `programs/AHU程序/云霞县华龙科技/flows_20251229175702.json`
- `programs/AHU程序/泰安宁阳中医院/flows_20260206160555.json`
- `programs/机房群控程序/20230707_机房群控示例程序{2主机+3冷冻冷却水泵+2冷却塔].json`
- `programs/机房群控程序/风冷热泵标准控制程序[风冷涡旋]20240905.json`

最低通过标准：

- 能解析。
- 能识别页签。
- 能生成边。
- 能生成总览图。
- 未识别内容有诊断，不崩溃。
- 命名匹配能输出统计。

### 11.3 未知内容降级

新项目出现未知结构时，系统应降级展示：

```text
未知页签
未知模块
未归类点位
未识别子流程
未匹配命名
悬空连接
```

这些都应进入诊断报告，不能静默丢弃。

## 12. 开发路线

### 12.1 阶段一：解析与中间模型

目标：稳定解析所有样例 JSON。

交付：

- JSON 加载器。
- 节点、页签、子流程、边模型。
- `wires` 方向转换。
- 节点类型统计。
- 页签节点统计。
- 诊断报告。

验收：

- 5 个样例全部解析成功。
- 边数量、节点数量、页签数量可输出。
- 对悬空引用、未知归属有诊断。

### 12.2 阶段二：命名规则匹配

目标：把 `data/naming_rules.json` 接入点位模型。

交付：

- 名称规整器。
- 精确匹配。
- compact 匹配。
- 冲突候选输出。
- 未匹配清单。
- 命名匹配统计。

验收：

- 每个样例输出命名统计。
- 未匹配点位可定位到节点。
- 冲突候选可查看。

### 12.3 阶段三：AHU 总览图 MVP

目标：针对三山经开区 AHU 生成第一张可用总览图，同时不写死项目。

交付：

- profile 自动识别。
- AHU 总览图。
- 关键模块摘要。
- 右侧详情面板数据。
- 导出中间图 JSON。

验收：

- 三山经开区 AHU 总览图包含 `IO/通讯`、`控制`、`定时`、`直膨机状态`。
- 云霞和泰安宁阳 AHU 也能生成类似总览图。
- 多出的 `排风机`、`直膨机故障` 能显示为额外页签模块。

### 12.4 阶段四：交互前端

目标：用户可以上传 JSON 并浏览流程图。

交付：

- 上传 JSON。
- 示例项目选择。
- 总览图画布。
- 模块详情面板。
- 搜索。
- 命名异常清单。
- 视图切换。

验收：

- 用户上传三山经开区 JSON 后能看到总览图。
- 点击模块能查看输入、输出、原始节点。
- 搜索点位能定位。
- 未匹配命名能高亮。

### 12.5 阶段五：模块详情图

目标：实现页签内部抽象图。

交付：

- 控制页模块图。
- IO/通讯信号流图。
- 直膨机状态矩阵。
- 定时页小图。
- 原始节点追踪视图。

验收：

- 控制页不直接铺 300 多个节点，而是按模块聚合。
- 直膨机状态页以重复状态矩阵展示。
- 定时页可以显示完整逻辑。

### 12.6 阶段六：AI 辅助

目标：在确定性功能稳定后接入 AI。

交付：

- 模块解释。
- 未匹配命名候选。
- 输出影响因素解释。
- 汇报版说明生成。

验收：

- AI 输出引用真实节点、点位或模块。
- AI 不改变确定性解析结果。
- 用户可关闭 AI。

## 13. MVP 验收标准

第一版 MVP 建议以三山经开区 AHU 为主验收，但必须通过其他样例的兼容性检查。

### 13.1 功能验收

- 支持上传 JSON。
- 支持选择仓库内示例 JSON。
- 能解析页签、节点、子流程、连接。
- 能生成系统总览图。

- 能显示命名匹配状态。
- 能列出未匹配和冲突命名。

### 13.2 用户体验验收

- 甲方能看懂系统由哪些部分组成。
- 工程人员能查看模块输入输出。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 只按三山经开区写规则 | 新项目无法适配 | 解析层通用，抽象层 profile 化，多样例回归 |
| 命名规则匹配率低 | 图中大量未匹配 | 多级匹配、候选建议、人工确认 |
| 原始节点太多 | 图不可读 | 三层视图、默认抽象、局部展开 |
| 自动布局混乱 | 用户看不懂 | 总览图手工规则布局，复杂图再用布局算法 |
| AI 幻觉 | 误导用户 | AI 只解释和建议，必须引用真实节点 |
| 新节点类型未知 | 解析失败 | 未知节点按通用节点展示，并进入诊断 |
| 甲方不认可抽象粒度 | 返工 | 提供简版、标准版、详细版三种粒度 |
